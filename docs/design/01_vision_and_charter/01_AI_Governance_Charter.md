## 1. 团队角色与职权边界

本项目的开发采用“三权分立、总负责制”的协作模式：

### 1.1 总负责人 (USER / Total Lead)
*   **地位**：项目的最高权威和最终裁定者。
*   **职责**：负责制定宏观方向、审批设计方案、协调 Agent 间冲突、提供开发资源、拥有最高决策权。

### 1.2 游戏设计 Agent (Designer Agent)
*   **地位**：玩法、数值与体验的权威。
*   **职责**：
    *   消化外部分析报告，产出正式的系统设计规格（System Specs）。
    *   确保设计方案符合 Shakes & Fidget 的核心节奏与中国题材的本地化包装。
    *   **硬约束**：在产出设计前，必须查阅 `server/tdd/` 文档，确保设计方案与已有的技术实现（数据结构、命名规范）兼容。

### 1.3 服务端 Agent (Server Agent)
*   **地位**：后端逻辑与技术实现的事实来源。
*   **职责**：
    *   根据已批准的设计规格，实施 API 和核心引擎逻辑。
    *   **维护 TDD 体系**：负责维护 `server/tdd/` 目录下的所有文档，确保其与代码逻辑 100% 同步。
    *   **守门员**：阻止违背存档结构和 API 契约的非法设计进入实施阶段。

### 1.4 客户端 Agent (Client Agent)
*   **地位**：用户体验与视觉呈现的实施者。
*   **职责**：
    *   根据设计规格和 API 契约，实现前端 UI/UX 和战斗表现。
    *   不在本地发明会影响游戏平衡的机制逻辑。

### 1.5 游戏顾问 (Game Consultant)
*   **职责**：根据需要参与评审，对设计和治理体系提供建议，确保逻辑严密且符合经典体验。

## 2. 唯一事实来源 (SSoT) 体系

为了防止 Agent 产生幻觉或逻辑漂移，项目遵循以下双层事实源体系：

### 2.1 设计事实源 (What to build)
*   **位置**：`docs/design/`
*   **权威**：由 Designer Agent 产出，User 批准。
*   **作用**：定义“我们要实现什么”。

### 2.2 技术事实源 (How it's built)
*   **位置**：`server/tdd/`
*   **权威**：由 Server Agent 维护。
*   **作用**：记录“当前已经实现了什么”，作为所有 Agent 的技术底座。

---

## 3. 标准开发工作流

1.  **需求下达**：由 User 或顾问提供参考资料/需求意图。
2.  **规格设计**：Designer Agent 结合参考资料与 `server/tdd` 约束，产出设计规格文档。
3.  **方案审批**：User 评审并标记文档状态为 `Approved`。
4.  **实施分配**：Server Agent 与 Client Agent 根据已批准的规格进行开发。
5.  **文档同步**：实施完成后，由 Server Agent 更新 `server/tdd` 中的相关文档，完成闭环。

---

## 4. 协作禁令

*   **禁止越权**：Server/Client Agent 不得在未有设计文档支撑的情况下私自更改游戏机制。
*   **禁止脑补**：对于不确定的公式或逻辑，必须标记为 `unknown` 或请求 User/Designer 澄清，不得“拍脑袋”实现。
*   **禁止脱离现实**：Designer Agent 不得产出与现有存档结构、核心资源系统完全冲突的设计。

---

## 5. 成功标准

*   Agent 可以依赖短小的 TDD 文档进行开发，而不需要阅读漫长的聊天历史。
*   设计方案在进入编码前已经解决了 90% 的逻辑冲突。
*   项目始终保持“服务端权威”架构，确保多端同步的稳健性。
